### Про `uv` — поправка

`uv` присутствует в PATH в двух экземплярах:

```
C:\Users\alexa\AppData\Local\hermes\bin\uv.exe                    ← первый в PATH
C:\Users\alexa\AppData\Local\Programs\Python\Python313\Scripts\uv.exe
```

Версию `0.12.15` показал **первый путь — копия внутри Hermes**. Это внутренняя
зависимость чужого агента, не твой инструмент и не твоя конфигурация.

Дыра GHSA-2cv4-cqwr-gwf7 (path traversal при установке wheel на Windows,
исправлена в 0.12.18) касается только запуска `uv` для установки пакетов. У тебя
такого сценария нет: `uv.lock` нет ни в одном проекте, кроме упоминания в
учебном README.

**Вывод:** обновление `uv` — не задача пользователя. Первая версия отчёта
назвала это «единственной настоящей находкой в твоём окружении», что неверно:
проверялась чужая копия в чужом каталоге.

## Три ошибки первой версии — как не повторять

| Ошибка | Как выглядела | Правило |
|---|---|---|
| Чужой хост назван твоим | `bkr.sudrf.ru` найден в меню sudrf.ru, оттуда сделан вывод «твои парсеры сломаны» | Утверждение о проекте — только по чтению кода |
| Чужая база не прочитана, но описана | Раздел о `knowledge/` с тремя утверждениями, база не открывалась | Не утверждать о содержимом того, что не читал |
| Чужой инструмент назван твоим | Версию `uv` дала копия внутри `AppData\Local\hermes\bin`, названа проблемой окружения | У любой утилиты проверять `Get-Command -All`: первый путь в PATH может вести не туда |

Общий знаменатель: **во всех трёх случаях следствие выдавалось за причину, а
принадлежность объекта устанавливалась по умолчанию.**
