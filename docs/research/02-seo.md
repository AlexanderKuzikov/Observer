# Часть 2. SEO и разработка сайтов

Проверено 2026-10-01 по официальной документации Яндекса и Google. Яндекс-доктрина
отдаёт `llms.txt` + `.md`-версии страниц — лимиты взяты оттуда, не из пересказов.

Три расхождения с памятью, которые стоит зафиксировать:
1. API Словостата больше нет на `yandex.ru/dev/wordstat/` (404) — переехал в
   Yandex Cloud Search API v2 и стал платным 18.05.2026.
2. У Яндекса **нет Core Web Vitals** вообще.
3. Вебмастер API получил платный слой PRO (30 000 ₽/мес) — раньше не было.

## 1. Core Web Vitals: точная формулировка

### Google — официально

> "Core Web Vitals is a set of metrics that measure real-world user experience
> for loading performance, interactivity, and visual stability of the page. We
> **highly recommend** site owners achieve good Core Web Vitals for success with
> Search… This, along with other page experience aspects, **aligns with what our
> core ranking systems seek to reward**."
> — `developers.google.com/search/docs/appearance/core-web-vitals`, обновлено
> 2025-12-10

Обратить внимание: это **«recommend» + «aligns with»**, а не «is a ranking
factor». Google намеренно смягчил язык с 2021 года.

Пороги (p75, мобильный и десктоп раздельно):

| Метрика | Порог |
|---|---|
| LCP | ≤ 2,5 с |
| INP | ≤ 200 мс |
| CLS | ≤ 0,1 |
| TTFB (экспериментальная) | ≤ 800 мс |

**INP заменил FID в 2024.** Критично: **Lighthouse не может измерить INP** —
нет реального пользовательского ввода. В лаборатории использовать **TBT** как
прокси.

### Яндекс — официально

Core Web Vitals в Яндексе **не существует**. Ни в одном официальном документе
нет ни LCP/INP/CLS, ни утверждения о влиянии на ранжирование.

> "Скорость загрузки страниц сайта это один из важных показателей его качества.
> Из-за низкой скорости пользователь может не дождаться открытия страницы и
> перейти на другой ресурс. Это снижает уровень доверия к сайту, **его
> посещаемость** и влияет на другие статистические показатели."
> — `yandex.ru/support/webmaster/ru/yandex-indexing/page-speed.md`

В этой же странице блок «Индекс скорости сайта … находится в бета-тестировании»
**закомментирован** — раздел выпилен.

Официальный список «что улучшает позиции» (`…/yandex-indexing/rank.md`):
Качество, Безопасность, Удобность, Польза, Представление в результатах.
Скорости и CWV там нет.

В доктрине качества (`…/search-quality.md`) вместо CWV:

| Метрика | Что значит |
|---|---|
| **Проксима** | Аспект включает «удобство потребления контента пользователем» — ближайший аналог скорости |
| **Профицит** | Полезность выдачи, включает клики **и полностью бескликовые взаимодействия** |
| **ИКС** | Индекс качества сайта — метрика, которой Яндекс меряет качество |

Проксима и Профицит — приёмочные метрики для A/B-экспериментов на алгоритмах.

**Вывод для работы с клиентами:** если спрашивают «нужно ли нам LCP ≤ 2,5 с ради
Яндекса» — официального подтверждения нет. Оправдывать как UX/поведенческие
факторы, а не как фактор ранжирования Яндекса.

Детали по Словостату для автоматизации:

- 4 метода: `/v2/wordstat/topRequests`, `/dynamics`, `/regions`, `/getRegionsTree`
- `folderId` **обязателен** в теле каждого запроса, роль `search-api.webSearch.user`
- Числа приходят **строками** (gRPC int64 → JSON) — кастовать `int()`
- В `dynamics` для `PERIOD_MONTHLY` поле `toDate` — **последний день месяца**
- Чего нет против веб-Вордстата: сравнение нескольких фраз в одном запросе,
  полные «левая/правая колонки», история запросов пользователя
- Операторы (`!слово`, `[слово]`, `-слово`) официально **не задокументированы**,
  но фактически работают (стороннее сообщество, не Яндекс)
- Грабли: `folderId` ровно 20 символов; лишний пробел при копировании из UI →
  `PERMISSION_DENIED`

## 7. Про DevTools MCP в контексте сайтов

Закрывает исходный вопрос с полным пониманием.

**Да, окупается, но по конкретной причине:** CLS и LCP на реальных страницах.
Причины CLS — img без `width`/`height`, поздние шрифты, рекламные слоты, вброс
баннера. Трейс инсайтами пинпоинтит **конкретный узел**.

При этом:

- Для **аудитов** всё равно нужен Lighthouse CLI, а не MCP: воспроизводимо,
  ставится в CI, не ест контекст агента.
- DevTools MCP нужен как **отладчик**: Lighthouse сказал «LCP плохой» → trace
  инсайтами называет конкретный виновник.
- Инсайты отправляют URL трейсов в **Google CrUX API**. Для небольших
  российских сайтов field-данных нет (нет достаточной выборки), поэтому флаг
  `--no-performance-crux` — не потеря фичи, а отказ от бесполезного исходящего
  запроса к Google.
- Заменой Playwright MCP он не является: Chrome-only (нет WebKit/Firefox),
  локаторы слабее, нет `browser_run_code_unsafe`.

Конфигурация для RU-контекста:

```json
"chrome-devtools": {
  "type": "local",
  "command": ["npx", "-y", "chrome-devtools-mcp@latest",
    "--headless", "--no-usage-statistics", "--no-performance-crux"],
  "enabled": true
}
```
