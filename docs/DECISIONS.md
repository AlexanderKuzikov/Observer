## ADR-001. Репозиторий без кода

**Дата:** 2026-10-01
**Статус:** принято

### Контекст

Пользователь смещает фокус на разработку сайтов и SEO, параллельно
рассматривает юридическое и бухгалтерское направления. Требуется опора на
исследование инструментов и внешних API, а не реализация.

По корневым правилам `D:\GitHub\AGENTS.md` код каждого проекта живёт в
отдельном репозитории. Смешивать исследовательские заметки с кодом — значит
тащить в каждый проект контекст, который ему не нужен.

### Решение

`Observer` — репозиторий **только с документацией**. Исследование не смешивается
с реализацией. Каждая будущая реализация — отдельный проект.

### Последствия

- Исследование живёт своей жизнью, не зависит от темпа разработки.
- Результаты переиспользуются как основание для решений в других проектах.
- Нет риска, что заметки превратятся в «полуготовый код».

## ADR-002. Отчёт разбит по направлениям, а не по инструментам

**Дата:** 2026-10-01
**Статус:** принято

### Контекст

Первая попытка дать отчёт в чате дала «малопонятную кашу»: смешаны браузеры,
SEO, госреестры, бухгалтерия и стек. Причина — попытка охватить всё в одной
плоскости, без границы между областями применения.

### Решение

Деление по **направлениям работы**, а не по типу инструмента. Каждая часть
самодостаточна и имеет собственную рекомендацию. Инструмент, полезный в двух
направлениях, описывается в обоих.

Дополнительно: главный отчёт содержит только сводку, матрицу приоритетов и
план — без деталей, чтобы был вход в тело.

### Последствия

- Можно прорабатывать одну часть, не читая остальные.
- Дублирование между частями — осознанная плата за автономность.
- Нумерация частей `01`…`06` стабильна и не переставляется.

## ADR-003. Факты и выводы разделены статусами

**Дата:** 2026-10-01
**Статус:** принято

### Контекст

Значительная часть находок — это живые HTTP-коды и чтение первоисточников,
которые протухают за недели. Смешанные с выводами и сомнениями, они выглядят
одинаково убедительно.

### Решение

Каждая находка помечена: ✅ проверено первоисточником (с датой и кодом),
⚠️ расхождения в источниках, ❓ не удалось проверить. Отдельный раздел
«что не удалось верифицировать» — чтобы отличать факт от домысла.

### Последствия

- Отчёт можно цитировать, не перепроверяя.
- Устаревание заметно по датам, а не по молчаливой неверности.
- Домыслы не маскируются под факты.

## ADR-004. Не включать рекомендации по продуктам без ответа пользователя

**Дата:** 2026-10-01
**Статус:** принято

### Контекст

Направления «юридическое» и «бухгалтерское» — перспектива, а не текущая
работа. Легко скатиться в проектирование продукта, который не нужен.

### Решение

Отчёт даёт технические точки входа и лицензионные риски, но не проектирует
продукт. Вопросы «нужен ли свой продукт на ГИС МТ» и «нужна ли лицензионная
чистота 1С» вынесены в открытые вопросы `CONTEXT.md`.

### Последствия

- Нет преждевременных архитектурных решений.
- Проработка направлений начинается с ответа пользователя, а не с чтения.

## ADR-005. Отчёт не содержит утверждений о проектах пользователя

**Дата:** 2026-10-01
**Статус:** принято

### Контекст

Первая версия отчёта содержала утверждения о коде пользователя, полученные не
чтением кода, а косвенными признаками:

1. «Твои парсеры могут быть сломаны — проверь `bkr.sudrf.ru`». Хост найден в меню
   самого sudrf.ru. Проверка `rg` по всем репозиториям показала: **не
   используется нигде**. В судебных проектах — региональные хосты
   `*.perm.sudrf.ru`, они отвечают 200.
2. Раздел «Зависимость от knowledge/» с тремя утверждениями о содержимом базы
   знаний. **База не открывалась ни разу.** Утверждения выведены из веб-поиска и
   подставлены под содержимое чужой базы.

Третьим следствием стали продуктовые рекомендации вроде «переезжай с PyMuPDF
из-за AGPL», «замени tsup», «выкинь imagemin». Проверка `package.json` показала:
PyMuPDF не используется нигде, `tsup` — только в одном проекте, `imagemin` и
`squoosh` — нигде.

### Решение

Отчёт описывает **только внешний мир**. Утверждение о проекте пользователя
допустимо только при чтении его кода или при явном ответе пользователя. Доказательством
не являются: наличие папки, имя репозитория, содержимое `README`.

Проверенные факты о коде вынесены в `CONTEXT.md` с указанием способа проверки.

Отдельно запрещено утверждать что-либо о содержимом `knowledge/` без
разрешения пользователя.

### Последствия

- Отчёт не может быть неверным о коде пользователя — некорректные утверждения
  не попадают в него вовсе.
- Рекомендации по внедрению требуют чтения конкретного проекта, а не папки.
- Для вывода «у тебя X» нужен `rg` по конкретным файлам — это дешевле, чем
  ошибочная рекомендация.
